DoubleSlash architecture

Identity lives on the device. Desktop and Android clients share a Rust core. Connections are negotiated between peers. Supernodes help move the bytes, without becoming the authority behind the conversation.

01 / Topology

Peers first. Infrastructure optional.

Each client owns identity, trusted peers, conversations, and room definitions. Desktop (Qt / QML) and Android (Kotlin / Compose) share the same Rust core. Direct and relayed sessions expose the same channel model: reliable streams, unidirectional streams, and datagrams.

No account service

A signed HTTPS invite bootstraps trust. There is no first-party identity, discovery, or presence backend and no central feature registry.

One feature framework

Voice, chat, files, video, rooms, and games sit on capability negotiation. Client UI consumes the framework rather than bypassing it.

02 / Security model

Trust the peer. Limit the relay.

Ed25519 identities sign invites and signaling. The invite handshake binds its transcript and derives a session key with X25519 and HKDF. Post-handshake signaling checks signatures, timestamp freshness, and replay protection.

Visible to a supernode

  • Peer and device identities, room membership, and routing identifiers.
  • Connection timing, message types, signatures, and byte volumes.
  • Room names and file-offer metadata, including filename and advertised size.

Not available to a supernode

  • Decrypted room chat, voice, video, or shared-audio content.
  • Plaintext file chunks or room content keys.
  • A stored conversation archive or file cache for later delivery.

Privacy is not anonymity: routing metadata remains visible. Direct relay encryption uses a static pairwise key and does not provide forward secrecy. Room content fails closed when real group-key material is unavailable.

From a room you are in, you can offer a member a personal invite sealed to them. Redeeming it requires their key, and trust begins when they accept.

How room keys are distributed

The elected keyer is the member with the lexicographically smallest normalized public ID currently in the room. It mints the first key once another member is present, seals the current epoch to each member, and rotates the key when someone leaves. A member that restarts, or that sees a newer epoch it cannot open, asks that keyer for the current epoch. The request is sealed, so a supernode forwards it without reading it. Receivers install a key only from the elected keyer, and only for a plausible epoch. Room chat, voice, video, shared audio, and file chunks wait until a real distributed key is installed.

Where replay protection differs

Signed signaling uses a five-minute freshness window and a per-sender signature replay guard. Real-time room audio and receiver-idempotent ordered file payloads skip signature deduplication, but still require valid signatures and fresh timestamps.

03 / Session lifecycle

From an invite to a usable channel.

  1. Accept a signed invitePeople share https://doubleslash.space/i#…. The landing page hands the fragment to the native client locally, as detailed below. A personal invite works once, within 15 minutes, and only on the device that created it. Restarting that device invalidates invites it already minted. A sibling device of the same identity refuses an invite it did not mint. The joiner waits five seconds for the minting device to accept before treating that refusal as final. The authenticated handshake uses ephemeral X25519, transcript binding, and expiry checks. The client persists trust locally. Supernode identity comes from the signed invite.
  2. Exchange capabilitiesCAPABILITY_ANNOUNCE advertises supported features. Matching IDs and major versions define the negotiated intersection.
  3. Establish transportDirect sessions use an embedded quinn::Endpoint. A supernode relay uses identity-authenticated QUIC. Signaling prefers an established QUIC stream, with WebSocket fallback. A connected trusted supernode can coordinate UDP hole punching; this path does not use STUN.
  4. Invoke an agreed featureFeature intersection, authentication tier, and required user consent are checked before dispatch. Inbound and outbound traffic is quota-controlled. An authenticated relay connection alone does not authorize application traffic.

An invite URL, from browser to app

In https://doubleslash.space/i#INVITE_PAYLOAD, INVITE_PAYLOAD stands for the encoded invite. Room links use /r in place of /i.

Our landing-page script reads location.hash, shows an unverified preview locally, and hands the payload to the installed desktop app through doubleslash://invite#INVITE_PAYLOAD or doubleslash://room#INVITE_PAYLOAD. It does not upload the payload. The native client validates the invite; opening the web page does not establish trust. If the app is not installed, the page offers a download link and a button to copy the complete invite.

When direct calling stalls

After call acceptance, a five-second direct-connect deadline can trigger a temporary private SFU room on a mutually trusted connected supernode. Pending fallback is canceled if direct transport recovers or the call ends.

When a client restarts

Relay grants and supernode information prefer the live WebSocket, so an old QUIC queue cannot capture reconnect replies. Portal requests wait for relay readiness outside the manager event loop, with a bounded timeout. Relay tickets renew automatically, and the endpoint mailbox retains reconnection information for 24 hours.

04 / Capability layer

Features are contracts, not side channels.

doubleslash-features is shared by clients and supernodes. Its registry owns descriptors, authentication tiers, consent, quotas, and channel framing. Optional features do not become mandatory services.

05 / Hosted experiences

Games are one consumer. Apps can use the same foundations.

A shared drawing surface and a multiplayer game have similar connectivity needs: load an interface, identify the participants, join a session, and exchange updates. DoubleSlash separates the hosted interface from the peer data path, so those building blocks can also support collaborative tools and node-specific portals without introducing a central account service.

Host the interface

web.host.app.v1 serves HTML, CSS, JavaScript, and assets from the supernode's web/ and games/ directories. Desktop uses Qt WebEngine; Android uses WebView. Pages load through d:// over QUIC bidirectional request/response streams. Chromium rewrites that scheme to doubleslash:// so Windows does not treat d: as a drive. This hosts an interface; it does not provide an application database.

Use the native bridge

window.doubleslash.ready supplies the local peer identity, supernode identity, and portal APIs. Channel open, send, poll, and close operations use the authenticated relay connection through /_doubleslash/channel/*. Portal fetches reach the hosting node without a separate public HTTP endpoint. External HTTPS pages must not keep this native bridge attached.

Exchange session updates

The DoubleSlashClient JavaScript SDK opens a named session and sends bytes through game.relay.v1. Pointers, drawing, and game-state updates can share this opaque datagram fan-out. The relay routes bytes without parsing them; that is not proof the application sealed its payloads.

Add a distinct contract

A new cross-peer service belongs in an explicit x.<vendor>.* capability, with its own version, authentication tier, consent, and quotas. The Rust framework supports request, stream, and datagram features. Registering a module does not automatically expose it to JavaScript: a consumer and any required bridge integration must also be implemented.

An access portal, step by step

  1. Establish the invited relationshipThe native client authenticates to the supernode. Where its access policy requires a gate, the node can issue a portal-only relay grant rather than full service access.
  2. Load the gate on the restricted connectionThe page is reachable over web.host.app.v1 while room membership, relay datagram forwarding, and reliable relay signaling remain unavailable to the portal-only guest.
  3. Resolve access against the authenticated peer/api/access/status reports the caller's access state; /api/access/accept requests admission. The node binds these operations to the QUIC peer identity, not a page-supplied account name.
  4. Enter the permitted experienceOnce granted, the client can establish full relay access. Feature negotiation, consent where required, and room membership still apply; passing the portal gate does not bypass them.

What the framework supplies

  • Device-held identity and authenticated transport.
  • Hosted in-app interfaces and a native channel bridge.
  • Feature contracts, authorization gates, and traffic quotas.
  • Opaque relay forwarding without server-side gameplay logic.

What an app must still design

  • Its data format, validation, and participant permissions.
  • Loss handling: datagrams can be dropped or arrive out of order.
  • State recovery and late-join snapshots from participating peers.
  • End-to-end protection for private app payloads; opaque forwarding alone is not encryption.

Hosting is a separate trust boundary: the operator supplies the page's code and assets. An authenticated connection identifies the host; it does not make arbitrary hosted JavaScript trustworthy. The game SDK currently routes through game.relay.v1; passing another feature ID does not invoke a custom module. Native room chat, voice, and files stay in the desktop and Android clients. A WASM plugin sandbox remains future work; native plugins run in-process.

06 / Content paths

Different media. Deliberate delivery.

Voice

Opus audio travels over QUIC datagrams. Room voice can fall back to signed WebSocket messages. Room audio is end-to-end sealed; active-speaker forwarding uses packet arrival, not decoded sound.

Video

VP9 and VP8 ship on every platform, from the vendored libvpx. Windows also encodes and decodes Media Foundation H.264. Direct calls negotiate a common codec, preferring H.264, then VP9, then VP8. Rooms default to VP9, because every member has to decode the sender’s codec. A room sender that falls behind on VP9 encoding switches to VP8 for the rest of that session, and each frame carries the codec in use. A direct peer receives that switch when it advertised VP8, or when it has not announced codecs yet. H.264 enters a room when chosen in Settings. Display of that codec is a Windows capability. Room video stays on QUIC relay datagrams, so a member reached only over WebSocket keeps the voice path. Picture-in-picture is composited into that one outgoing stream.

Shared audio & synchronization

A session clock timestamps video and shared audio together. Audio-led playout holds or drops video to synchronize it; video without a current audio anchor free-runs. Shared audio follows the viewed video, independently of voice mute. Adaptive bitrate is implemented. Android has no shared-audio playback consumer yet.

Files are offered, then pulled

Room file offers contain metadata, not an automatic upload. An accepting member requests chunks from the originator, which sends only to that recipient from disk. The offer also reaches the sender’s other devices, so one of your devices can pull a file another of your devices offered. Transfers above 8 MiB stream uncompressed, without delta encoding. The maximum size is 4 GiB. Revoking an offer stops further downloads but cannot remove copies already received. The supernode stores no file cache.

07 / State & operations

Durable on clients. Ephemeral on relays.

Where state belongs
OwnerPersistent stateRuntime state
Native clientIdentity, trusted peers, local chat history, settings, encrypted room definitions, optional device registries. Encrypted .dbackup snapshots can move a profile.Sessions, negotiated capabilities, media pipelines, room keys.
SupernodeIts identity, peer trust, feature manifest, invite configuration, endpoint mailbox.SFU rooms, membership, routing, quotas, and cluster links. No content archive. User-created rooms idle-GC after 15 minutes.

Clients rematerialize saved rooms on connection. Room chat history is keyed by room ID, so changing the hosting supernode does not split the conversation. Empty user-created rooms are collected after 15 minutes; the built-in default room remains. Removing a room from the sidebar is a local hide, not a remote delete. Public user-created rooms are disabled by default (room.audio.sfu creation policy). Two of your own devices can exchange a sealed room snapshot. The receiver adds rooms from it, and leaves existing rooms, names, types, and local hides as they are.

Cluster replication

Members exchange room existence, client trust, Space roots, and opaque room frames (chat, audio, and camera on/off) over authenticated cluster QUIC links. They do not replicate private-room per-peer ACLs. Space proofs, local invite tokens, and creator admission cover room access.

Cluster operations

The separate supernode manager provisions and deploys nodes over SSH. Cluster UDP ports are restricted to member IPs. Redeploy preserves the roster and cluster firewall rules; roster changes use an explicit cluster sync.

08 / Implementation

Four workspaces. Clear ownership.

doubleslash-client

Desktop workspace. Qt / QML connects through CXX-Qt models and AppBridge to ConnectionManager, local stores, and media pipelines. The optional Ollama assistant lives here. Headless builds support tests.

doubleslash-android + android/

JNI bridge and Kotlin/Compose UI sharing the same Rust core. Ordinary features use a JSON command/event channel. Camera frames, and the surfaces that show incoming video, use dedicated interfaces.

rust/

The outer workspace contains the shared features registry, supernode, installer, and first-party Opus and VP8/VP9 wrappers. The installer handles release download, verification, and application.

doubleslash-supernode-manager

Separate operations workspace. Inventory, SSH transport, provisioning, cluster configuration, and a CLI / terminal dashboard. It is not an identity backend.

Invites people share are https://doubleslash.space/i#…. The in-app portal navigates d://; Chromium uses doubleslash:// as the Windows-safe alias and as the landing-page handoff into an installed desktop client. Crate names, the QUIC TLS server name, HKDF labels, window.doubleslash, and /_doubleslash/channel/* stay as they are so existing sessions keep working.

09 / Current state

Implemented does not mean finished everywhere.

IMPLEMENTED
  • Direct and relayed QUIC, capability negotiation, and room content sealed with a real group key.
  • Desktop and Android clients sharing one Rust core, plus encrypted backups that restore as a separate profile.
  • VP9 and VP8 on every platform. Windows also has Media Foundation H.264, screen/window capture, and shared audio.
  • A/V sync, adaptive bitrate, Space Layer 1 trees and proofs, and default core.devices.v1 advertisement.
  • Encrypted own-device room-key handoff, and add-only room snapshots between your devices.
LIMITS & OPEN WORK
  • Linux and macOS camera hardware validation is pending. Screen and shared-audio capture are Windows features today.
  • Android incoming video is opt-in and has not been validated on a device. Shared-audio playback is not connected. Two-client and room media acceptance is still open.
  • Device pairing, continuous history sync, and installed simultaneous-use acceptance are unfinished. A file-based move means quitting the source device before connecting the destination.
  • Space Layer 2 cryptography and a WASM plugin sandbox are deferred. Native plugins run in-process.

Capture is a privacy boundary: whole-screen sharing includes pop-ups. On Windows versions below build 20348, per-application audio capture falls back to whole-machine audio rather than silence.
