DoubleSlash architecture

Identity lives on the device. Desktop and Android clients share a Rust core. Connections are negotiated between peers. Supernodes help move the bytes, without becoming the authority behind the conversation.

01 / Topology

Peers first. Infrastructure optional.

Each client owns identity, trusted peers, conversations, and room definitions. Desktop (Qt / QML) and Android (Kotlin / Compose) share the same Rust core. Direct and relayed sessions expose the same channel model: reliable streams, unidirectional streams, and datagrams.

No account service

A signed HTTPS invite bootstraps trust. There is no first-party identity, discovery, or presence backend and no central feature registry.

One feature framework

Voice, chat, files, video, rooms, and games sit on capability negotiation. Client UI consumes the framework rather than bypassing it.

02 / Security model

Trust the peer. Limit the relay.

Ed25519 identities sign invites and signaling. The invite handshake binds its transcript and derives a session key with X25519 and HKDF. Post-handshake signaling checks signatures, timestamp freshness, and replay protection.

Visible to a supernode

  • Peer and device identities, room membership, and routing identifiers.
  • Connection timing, message types, signatures, and byte volumes.
  • Room names and file-offer metadata, including filename and advertised size.

Not available to a supernode

  • Decrypted room chat, voice, video, or shared-audio content.
  • Plaintext file chunks or room content keys.
  • A stored conversation archive or file cache for later delivery.

Privacy is not anonymity: routing metadata remains visible. Direct relay encryption uses a static pairwise key and does not provide forward secrecy. Room content fails closed when real group-key material is unavailable.

A node proves who answers

An address from an invite, DNS, or DDDNS says where to dial, not who answers. A supernode must sign the client’s random hello challenge with its identity key before the client treats it as connected. The proof does not encrypt plain ws:// signaling.

Certificates name a key

QUIC certificates are self-signed and name an identity. The client accepts a peer or relay only when the TLS handshake is signed by the key that name claims.

From a room you are in, you can offer a member a personal invite sealed to them. Redeeming it requires their key, and trust begins when they accept.

How room keys are distributed

The elected keyer is the member with the lexicographically smallest normalized public ID currently in the room. It mints the first key once another member is present, seals the current epoch to each member, and rotates the key when someone leaves. A member that restarts, or that sees a newer epoch it cannot open, asks the elected keyer for the current epoch. That request is sealed, so a supernode forwards it without reading it. When the keyer is another device of the same identity, the device reopens the encrypted room-key handoff with that sibling instead. Receivers install a key only from the elected keyer, and only for a plausible epoch. Room chat, voice, video, shared audio, and file chunks wait until a real distributed key is installed.

Where replay protection differs

Signed signaling uses a five-minute freshness window and a per-sender signature replay guard. Real-time room audio and receiver-idempotent ordered file payloads skip signature deduplication, but still require valid signatures and fresh timestamps.

03 / Session lifecycle

From an invite to a usable channel.

  1. Accept a signed invitePeople share https://doubleslash.space/i#…, as a link or a QR code of the same URL. A personal invite works once, within 15 minutes, and only on the device that minted it; restarting that device invalidates it. The handshake uses ephemeral X25519, transcript binding, and expiry checks. Trust is stored locally, and whether the inviter is a supernode comes from the signed invite.
  2. Exchange capabilitiesCAPABILITY_ANNOUNCE advertises supported features. Matching IDs and major versions define the negotiated intersection.
  3. Establish transportDirect sessions use an embedded quinn::Endpoint on one dual-stack IPv4/IPv6 socket. A supernode relay uses identity-authenticated QUIC. Signaling prefers an established QUIC stream, with WebSocket fallback. A connected trusted supernode can coordinate UDP hole punching, without STUN.
  4. Invoke an agreed featureFeature intersection, authentication tier, and required consent are checked before dispatch, and traffic is quota-controlled in both directions. An authenticated relay connection alone does not authorize application traffic.

What the website sees of an invite

The invite sits after the #, and browsers do not send that part to the server. The landing page reads it locally, shows an unverified preview, and hands it to the installed app through doubleslash://invite#… or doubleslash://room#…. The app validates it; the page uploads nothing. Room links use /r in place of /i.

When direct calling stalls

If direct QUIC is not up five seconds after a call is accepted, the call moves to a temporary private SFU room on a mutually trusted supernode. That fallback is canceled if direct transport recovers or the call ends.

When an address changes

A supernode keeps each client’s latest endpoint for 24 hours, so peers can find each other after a restart or network change. To reach the node itself, clients dial the invite’s IP, then its optional hostname, resolved by DNS or an HTTPS DDDNS record. The node must still pass the identity proof.

04 / Capability layer

Features are contracts, not side channels.

05 / Hosted pages

Pages served by a supernode, opened in the app.

A supernode can serve pages and games that open inside DoubleSlash. They reach the node, and each other, over the client’s authenticated connection. There is no public web server.

Serve the page

web.host.app.v1 serves files from the node’s web/ and games/ directories over QUIC streams. Pages open at d://; Chromium uses doubleslash://, because Windows reads d: as a drive. Desktop uses Qt WebEngine, Android a WebView. It serves files; it is not a database.

Native bridge

window.doubleslash supplies the local identity and portal APIs. Channels use /_doubleslash/channel/* over the relay connection. External HTTPS pages never get this bridge.

Session updates

The JavaScript SDK sends bytes through game.relay.v1. The relay forwards them without parsing. That is not encryption: a page must seal its own payloads if they are private.

New services

A new cross-peer service needs its own x.<vendor>.* capability, with a version, authentication tier, consent, and quotas, and its own JavaScript bridge.

Seven demos are in the repository: Presence Playground, Brick Breaker, Shared Canvas, Task Board, Focus Timer, Four in a Row, and Memory Match. Their state lives only in open pages. x.doubleslash.matchmaker.v1 is an opt-in reference lobby module, not a running service.

Access gates

  1. Restricted until passedAn operator can require a gate. Until a client passes it, the client has portal-only relay access: the gate page loads, but rooms, datagram forwarding, and relay signaling stay closed.
  2. Bound to the peer identity/api/access/status reports the caller’s state and /api/access/accept requests admission, both bound to the QUIC peer identity rather than anything the page supplies. A code gate also needs the operator’s code. Grants survive a node restart.
  3. Full access, same rulesPassing the gate grants full relay access to that node. Feature negotiation, consent, and room membership still apply.

The operator supplies a hosted page’s code; an authenticated host does not make its JavaScript trustworthy. Native plugins run in-process, and a WASM sandbox is future work.

06 / Content paths

Different media. Deliberate delivery.

Voice

Opus over QUIC datagrams; room voice can fall back to signed WebSocket messages. Room audio is end-to-end sealed, and active-speaker forwarding uses packet arrival, not decoded sound. Decoding defaults to complexity 5, which turns on Deep PLC loss concealment; a 0–10 setting on both clients adds LACE at 6 and NOLACE at 7.

Video

VP9 and VP8 on every platform; Windows adds Media Foundation H.264. Direct calls negotiate a codec, preferring H.264, then VP9, then VP8. Rooms default to VP9 so every member can decode it, and a sender that cannot encode VP9 in real time switches to VP8 for the session. Room video uses relay datagrams only, so a member on WebSocket alone keeps voice but not video.

Shared audio & sync

Video and shared audio are stamped by one session clock. Playout follows the shared audio and holds or drops video to match it; video with no audio free-runs. Shared audio follows the video you watch, independently of voice mute.

Files are offered, then pulled

A room file offer is metadata. Members who accept pull chunks from the sender’s disk, including the sender’s own other devices. Offers last an hour. Files go up to 4 GiB, and above 8 MiB they stream uncompressed. A stalled download resumes from the first missing chunk up to three times, then waits for Retry. Revoking stops new downloads, not copies already made. Supernodes keep no file cache.

07 / State & operations

Durable on clients. Ephemeral on relays.

Where state belongs
OwnerPersistent stateRuntime state
Native clientIdentity, trusted peers, local chat history, settings, encrypted room definitions, optional device registries. Encrypted .dbackup files can move a profile.Sessions, negotiated capabilities, media pipelines, room keys.
SupernodeIts identity, peer trust, feature manifest, invite configuration, endpoint mailbox, access-gate grants.SFU rooms, membership, routing, quotas, and cluster links. No content archive.

Clients recreate their saved rooms on connection. Chat history is keyed by room ID, so moving a room between supernodes does not split it; the built-in default room, present on every node, keeps its history per supernode. Empty user-created rooms are collected after 15 minutes. Public user-created rooms are off by default.

Hide Room affects one device. Remove Room deletes the room on all your devices, optionally with its local history; other members keep it, and nothing is deleted on the supernode. Your devices exchange sealed room lists, and the later of an add and a removal wins.

Clusters

Servers in a cluster share room existence, client trust, Space roots, and opaque room frames over authenticated QUIC links. Each copy is deduplicated and never forwarded again. Private-room access is not replicated; it comes from Space proofs, invite tokens, or creator admission. Clients see a cluster as one supernode and fail over between its servers.

Hosting a node

The supernode manager deploys over SSH, from its CLI or from the desktop’s Settings › Network › Your servers. The desktop pins the host key, hardens Debian or Ubuntu, never stores the server password, pushes verified updates, and adds or removes cluster servers. Cluster ports are open only to member IPs. A new node gains trust only when you accept its signed invite.

08 / Implementation

Four workspaces.

doubleslash-client

Desktop: Qt / QML through CXX-Qt to ConnectionManager, local stores, and media pipelines. Includes the optional Ollama assistant and Your servers. One process runs each profile.

doubleslash-android + android/

JNI bridge and Kotlin / Compose UI on the same Rust core. Features use a JSON command/event channel; camera frames and video surfaces use dedicated interfaces.

rust/

Shared features registry, supernode, installer, and Opus and VP8/VP9 wrappers built from vendored source. The Microsoft Store package updates through Windows; other desktop installs use the installer, which verifies what it downloads.

doubleslash-supernode-manager

Operations: inventory, pinned SSH, provisioning, hardening, an on-server updater with rollback, and cluster configuration, with a CLI and terminal dashboard. The desktop builds it in. It is not an identity backend.

09 / Current state

What works, and what is still open.

IMPLEMENTED
  • Direct and relayed QUIC over IPv4 and IPv6, capability negotiation, and room content sealed with a real group key.
  • Desktop and Android on one Rust core. Encrypted backups that restore as a separate profile.
  • VP9 and VP8 everywhere; on Windows, also H.264, screen and window capture, and shared audio. A/V sync and adaptive bitrate.
  • Space Layer 1 trees and proofs, own-device room-key handoff and room sync, and Message myself.
  • Supernode identity proof, hostname and DDDNS fallback, and setting up and managing a supernode from the desktop.
LIMITS & OPEN WORK
  • Linux and macOS cameras are not validated on hardware. Screen and shared-audio capture are Windows only.
  • Android incoming video and shared audio are not validated on a device. Two-client and room media acceptance are open.
  • Device pairing, history sync, and simultaneous use of one identity on two installed devices are unfinished. Moving a profile by file means quitting the source first.
  • Desktop hosting is live-tested on one Debian 12 server. No client has looked up a live DDDNS record, and the DoubleSlash DDNS service is in test mode.
  • Signaling over plain ws:// is not encrypted to the node. Space Layer 2 and a WASM plugin sandbox are deferred.

Whole-screen sharing includes pop-ups and notifications. On Windows before build 20348, per-application audio capture falls back to whole-machine audio.
